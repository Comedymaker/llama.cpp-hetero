# CPU-only 投机采样根因剖析

## 实验目的

定位 OnePlus 13 上 CPU-only 投机采样无法稳定超过 target-only 的主要开销，并与 A40 的批量验证扩展性进行对照。

## 实验设置

- 日期范围：2026-05-11 至 2026-05-18
- 设备：OnePlus 13；A40 对照平台
- 后端：CPU-only 投机采样
- 5 月 11 日：扫描 draft window `gamma=1,2,4,8,16`
- 5 月 15 日：对比 A40 与 OnePlus 13 的 target-only、speculative-simple、验证吞吐和 draft prompt 同步成本
- 5 月 18 日：CNN/DailyMail；Qwen3-8B-Q4_K_M target；Qwen3-0.6B-Q4_K_M draft；`draft-max=8`；`ctx=4096`；生成 128 token；重复 3 次
- 其他阶段的完整参数和代码版本：原始记录未注明

## 实验结果

### 2026-05-11：不同 draft window

| gamma | Target verify 减少时间中位数 | Draft 额外开销 |
| ---: | ---: | ---: |
| 1 | 1041 ms | 3112 ms |
| 2 | 2148 ms | 4968 ms |
| 4 | 1165 ms | 5170 ms |
| 8 | 407 ms | 4118 ms |
| 16 | 2860 ms | 3502 ms |

所有窗口下都未稳定超过 target-only，draft/runtime 开销大于 target verification 节省的时间。

### 2026-05-12：draft 纯 decode 与上下文同步

- `draft_decode_tok_per_s` 约为 56 tok/s，draft 纯 decode 本身并不慢。
- `llama-speculative-simple` 每轮执行 prompt/context catch-up decode，将连续 decode 变成多个小 batch 和频繁同步。

### 2026-05-15：A40 与 OnePlus 13

| 指标 | A40 | OnePlus 13 |
| --- | ---: | ---: |
| Target-only | 87.19 tok/s | 9.07 tok/s |
| Speculative-simple | 98.65 tok/s | 7.98 tok/s |
| 加速比 | 1.13x | 0.88x |
| 接受率 | 57.7% | 62.8% |
| Target-only verify | 275.8 tok/s | 9.09 tok/s |
| Speculative verify | 726.5 tok/s | 13.89 tok/s |

| 平台 | Draft prompt 同步 token | 同步时间 | 平均每 token |
| --- | ---: | ---: | ---: |
| A40 | 373 | 70.0 ms | 约 0.19 ms |
| OnePlus 13 | 368 | 1329.1 ms | 约 3.61 ms |

- 手机接受率高于 A40，却仍然变慢，接受率不是主要原因。
- A40 能把 batch verify 转化为高吞吐；手机 CPU 更受内存带宽、cache 和小批量 GEMM 限制。
- Draft sync 的主要成本不是查找前缀或编辑 KV cache，而是为小模型补跑真实的 `llama_decode`。

## 实验结论

- 手机 CPU-only 投机采样的主要瓶颈不是接受率，也不主要是内存不足，而是较弱且不稳定的 batch verification 收益，以及高额 draft context sync 和 decode 成本。
- Draft 单跑较快不等于投机循环便宜；端侧循环中的小 batch、频繁同步和 context catch-up 会改变实际开销。
- A40 的 batch 收益随窗口基本单调扩展，手机 CPU 的扩展不稳定，节省的 target 验证时间不足以覆盖新增 draft 成本。
