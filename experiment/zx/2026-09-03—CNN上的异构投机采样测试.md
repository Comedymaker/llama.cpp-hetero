# CNN/DailyMail 上的 CPU-HTP 异构投机采样评测

## 实验目的

本实验在真实新闻摘要输入上评估 Qwen2.5-3B target model 与 Qwen2.5-0.5B draft model 的异构投机采样性能，重点回答异构方案相对 CPU 4 线程和 CPU 8 线程基线的性能关系。


实验期为 2026-09-03 至 2026-09-04。

## 实验设置

### 硬件与软件

| 项目 | 配置 |
| --- | --- |
| 手机 | OnePlus PJZ110（Snapdragon 8 Elite / SM8750） |
| CPU | Android CPU backend，实验线程数为 4 或 8 |
| NPU | Hexagon v79，HTP0；日志报告 6 HVX、1 HMX、8 MiB VTCM |
| GPU | Adreno 830，仅由编译产物枚举，本组对照不使用 OpenCL 推理 |
| target model | Qwen2.5-3B Q4_0，`qwen2.5-3b.q4_0.gguf`，约 1.6 GiB |
| draft model | Qwen2.5-0.5B Q4_0，`qwen2.5-0.5b.q4_0.gguf`，约 336 MiB |

### 数据集与输入构造

- 数据集：CNN/DailyMail 3.0.0 test split，来源为 `abisee/cnn_dailymail` 的 Parquet 文件。
- 固定随机种子：`221117192`。
- 样本筛选：文章按空白字符计数为 400 至 1400 个词。
- Prompt 模板：要求用 3 个简洁要点概括新闻，只使用文章支持的信息。
- 共准备 100 个样本，编号为 `cnn_dm_00` 至 `cnn_dm_99`；本轮规模化范围为前 80 个样本，即 `00-79`。
- 每个样本固定请求生成 128 token，并使用 `--ignore-eos`。这是吞吐和接受率测试，不是自然停止的摘要质量或真实任务时延测试。

| `05` | 751 | 9.61 | 17.88 | 16.405 | 81.651% |
| `06` | 863 | 10.09 | 17.73 | 15.647 | 75.000% |

| `08` | 875 | 10.78 | 17.91 | 13.325 | 61.417% |
| `09` | 619 | 9.66 | 18.79 | 15.581 | 68.033% |

### 前 10 篇汇总

| 指标 | CPU 4 | CPU 8 | CPU-HTP 异构 |
| --- | ---: | ---: | ---: |
| Prompt token 总数 | 8446 | 8446 | 8446 |
| 聚合 Prefill 吞吐 | 14.103 t/s | 24.884 t/s | 280.319 t/s |
| 聚合 Decode 吞吐 | 10.592 t/s | 17.099 t/s | 14.159 t/s |
| 逐样本 Decode 均值 | 10.786 t/s | 17.169 t/s | 14.350 t/s |
| 逐样本 Decode 标准差 | 1.605 t/s | 1.137 t/s | 1.674 t/s |
| Prefill + Decode 总时间 | 719.270 s | 414.226 s | 122.866 s |

前 10 篇上，异构 Decode 聚合吞吐相对 CPU 4 线程提高 `33.7%`（`1.337x`），10 个样本均快于 CPU 4 线程；但相对 CPU 8 线程低 `17.2%`（`0.828x`）。异构端到端时间相对 CPU 4 和 CPU 8 分别缩短约 `5.85x` 和 `3.37x`，主要来自 HTP 的 Prefill 优势，而不是投机 Decode 超过 CPU 8。

### 异构接受率与阶段耗时

| 指标 | 前 10 篇汇总 |
| --- | ---: |
| 实际输出 token | 1313 |
| Draft token | 1239 |
| Accepted token | 826 |
| 加权接受率 | 66.667% |
| 逐样本接受率均值 | 67.452% |
| 逐样本接受率标准差 | 10.071 个百分点 |
| Target verify calls | 487 |
| 每次验证接受 token | 1.696 |
| 每次验证产出 token | 2.696 |

| 阶段 | 累计耗时 | Decode 时间占比 |
| --- | ---: | ---: |
| Target decode / HTP 验证 | 62.756 s | 67.67% |
| Draft generate | 14.018 s | 15.12% |
| Draft process | 15.781 s | 17.02% |
| 其余阶段 | 0.181 s | 0.20% |

HTP 验证仍是异构 Decode 的主要瓶颈。接受率越低，单位输出 token 需要的验证调用越多，target 固定开销越难摊薄。样本 `04` 的接受率仅 44.667%，其异构 Decode 只有 10.598 t/s，是前 10 篇中最明显的低接受率慢样本。


## 实验结论

1. 已测结果表明，CPU-HTP 异构方案在 CNN/DailyMail 前 10 篇上的 Decode 吞吐为 14.159 t/s，比 CPU 4 线程快 33.7%，但比 CPU 8 线程慢 17.2%。因此当前方案已经超过较弱 CPU 配置，尚未超过性能正常的 CPU 8 线程。。
2. 异构 Decode 的主要耗时是 target 在 HTP 上的批量验证，占 67.67%；CPU draft generate 和 draft process 合计约 32.14%。继续优化时应同时减少验证调用次数和 CPU draft 管理开销，而不是只关注单独的 draft model 吞吐。
