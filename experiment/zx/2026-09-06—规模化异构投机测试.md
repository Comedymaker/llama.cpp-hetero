# CNN/DailyMail 规模化 CPU-HTP 异构投机测试

## 实验目的

本轮实验将前期少量 Prompt 测试扩展到 CNN/DailyMail 新闻摘要数据集，验证以下问题：

1. CPU-HTP 异构投机方案在更多输入上的 Decode 收益是否稳定。
2. CPU 4 线程、CPU 8 线程与 HTP target + CPU draft 的性能关系。
3. 投机窗口 `1/2/3/4/8/16` 对吞吐、接受率、验证次数和阶段耗时的影响。
4. 固定窗口后，置信度阈值 `p-min` 如何影响候选长度和验证效率。
5. 手机热状态、后台运行方式和自动参数选择是否会污染规模化实验。

实验从 2026-09-04 持续至 2026-09-06。所有计划中的 CPU 基线、窗口扫描和 `p-min` 扫描均已完成。

## 实验设置

### 硬件、模型与程序

| 项目 | 设置 |
| --- | --- |
| 手机 | OnePlus PJZ110，Qualcomm Snapdragon 8 Elite / SM8750 |
| CPU | Android CPU backend，4线程或8线程 |
| NPU | Hexagon v79，HTP0；6 HVX、1 HMX、8 MiB VTCM |
| Target | Qwen2.5-3B Q4_0|
| Draft | Qwen2.5-0.5B Q4_0|


### 数据集与统一参数

- 数据集：CNN/DailyMail 3.0.0 test split。
- 数据来源：`abisee/cnn_dailymail` Parquet。
- 筛选条件：文章按空白字符计数为400至1400词。
- 本轮使用：`cnn_dm_00` 至 `cnn_dm_79`，共80篇。
- Prompt：要求用3个简洁要点总结新闻，只保留文章支持的信息。
- 生成：`-n 128 --ignore-eos --temp 0 --top-k 1`。
- Context：`-c 4096`。
- KV cache：K/V均为默认F16。
- Flash Attention：`off`。

固定128-token输出用于吞吐和接受率对照，不代表自然EOS下的摘要长度，也不评估ROUGE或摘要质量。`llama-cli`日志通常将第一个生成token计入最后一次Prompt eval，因此请求128 token时Decode统计显示127次eval。投机程序可能在最后一批验证时越过边界，实际输出为129至133 token。

### 温控、断联和统计口径

- 每次运行前至少冷却60秒。
- 若电池温度高于38.0°C，则继续每60秒检查一次。
- 接受率为总 `n_accept / n_drafted`，而不是逐样本百分比的简单平均。


## 实验结果

### CPU 4线程与CPU 8线程基线

| 指标 | CPU 4线程 | CPU 8线程 |
| --- | ---: | ---: |
| 样本数 | 80 | 80 |
| Prompt token | 77,949 | 77,949 |
| Decode eval次数 | 10,160 | 10,160 |
| 聚合Prefill | 13.445 t/s | 24.623 t/s |
| 聚合Decode | 10.073 t/s | 16.988 t/s |
| 逐样本Decode均值 | 10.165 t/s | 17.071 t/s |
| 逐样本Decode标准差 | 1.037 t/s | 1.105 t/s |
| 变异系数 | 10.21% | 6.47% |
| 中位数 | 9.978 t/s | 17.327 t/s |
| 最小值 | 7.793 t/s | 11.715 t/s |
| 最大值 | 13.590 t/s | 18.652 t/s |
| 程序累计总时间 | 6810.219 s | 3768.103 s |

在正式温控条件下，CPU 8线程聚合Decode比CPU 4线程高68.65%。CPU 8线程没有复现此前长时间连续运行时降到 `0.x t/s` 的异常，说明那组异常主要受到热状态或调度状态污染，并不代表8线程的稳定性能。

窗口4获得最高吞吐且三轮最稳定。窗口从1增大到4时，每次验证产出增加，HTP验证次数下降；继续增大到8或16后，接受率显著下降，CPU draft工作量增长，收益被抵消。

与CPU基线的聚合Decode对比：

| 配置 | 相对CPU 4线程 | 相对CPU 8线程 |
| --- | ---: | ---: |
| `p-min=0.00` | +65.65% | -1.78% |
| `p-min=0.20` | +62.56% | -3.61% |
| `p-min=0.30` | +53.78% | -8.82% |

80篇结果中 `p-min=0.00` 数值最高，但三组80篇是在不同时间块顺序运行，运行前温度也不同：`p-min=0.00` 主要处于约36.5°C，`p-min=0.20` 后段约37.6°C，`p-min=0.30` 为更早的独立运行。由于全量测试没有按阈值逐样本交错，不能将1%至2%的差异完全归因于阈值。更加可控的20篇×3轮交错扫描仍支持 `p-min=0.20`，但只表现出0.45%的小优势。

`p-min=0.20` 的Prompt编码和Decode阶段合计约955.984 s；CPU 4和CPU 8程序累计推理时间分别为6810.219 s和3768.103 s。按这些程序各自报告的推理阶段时间估算，异构端到端分别约快7.12倍和3.94倍。该比较主要反映HTP Prefill优势；由于CPU与异构使用不同程序、异构会多输出少量token，不能把它视为完全相同计时边界下的严格微基准。

## 实验结论

1. 实测结论：CPU-HTP异构投机在80篇CNN/DailyMail上稳定超过CPU 4线程。根据 `p-min` 配置不同，聚合Decode提升53.78%至65.65%。
2. 实测结论：当前异构Decode仍未明确超过CPU 8线程。最接近的 `p-min=0.00` 低1.78%，`p-min=0.20` 低3.61%；这已经比最初窗口4、`p-min=0.30` 的8.82%差距更小。
3. 实测结论：窗口4是本轮扫描中的最佳窗口，聚合Decode为16.445 t/s，且3轮间标准差仅0.034 t/s。窗口过大会使CPU draft开销上升，窗口过小则无法充分摊薄HTP验证开销。
4. 实测结论：更高的 `p-min` 会提高条件接受率，但不必然提高吞吐。阈值0.40的接受率最高，却因验证次数增加和每次验证产出下降而最慢。
5. 阶段性判断：`p-min=0.20` 在严格交错的20篇×3轮扫描中取得最好且最稳定的结果，但其优势只有0.45%；不同时间块的80篇运行又出现 `p-min=0.00` 略快，因此当前证据更适合说明最优区域在0至0.30，而不足以证明单一阈值具有普遍最优性。
