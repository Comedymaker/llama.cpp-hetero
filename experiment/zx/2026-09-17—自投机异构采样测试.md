# 2026-09-17 自投机异构采样测试

## 1. 实验目的

本日实验验证 LayerSkip 自投机采样在手机 CPU/HTP 异构执行下的正确性与性能，重点回答以下问题：

1. CPU 前 8 层 Draft、HTP 后 24 层 Target 验证能否正确运行；
2. 常驻 HTP 的 Tail 是否能提高自投机吞吐；
3. `window=4` 和 `window=6` 在 HumanEval 与 CNN/DailyMail 新闻续写上的差异；
4. 异构自投机输出是否与纯 Target 一致；
5. 公开 LayerSkip checkpoint 在官方 CNN/DailyMail 摘要任务上的 ROUGE、接受率及输出行为是否与手机异常一致。

本文中的吞吐均优先采用程序输出的 `layerskip generation`，即只统计生成阶段，不包含 Prompt Prefill。除特别说明外，采样方式为 Greedy。

## 2. 实验环境

### 2.1 手机与模型

- 手机：OnePlus PJZ110
- SoC：Qualcomm SM8750
- 模型：`facebook/layerskip-llama2-7B`
- 手机模型格式：F16 GGUF
- 模型层数：32
- Early Exit：`E=8`
- CPU 线程：4
- Draft：CPU 执行 `[0, 8)` 层
- Target Tail：HTP 执行 `[8, 32)` 层
- 最终 LM Head：CPU

### 2.2 权重驻留方式

当前实现是在程序启动时加载一次完整模型：

- CPU 保留 Early Exit 所需的前 8 层；
- 后 24 层权重常驻 HTP，供每轮 Target 验证使用；
- 每轮验证不重新从闪存读取后 24 层权重。

实测设备内存分配约为：

| 设备 | 模型占用 |
| --- | ---: |
| CPU | 3588.27 MiB |
| HTP | 9264.75 MiB |

在 w4 总生成时间中：

- Draft Build：约 28.1%；
- Tail Verify：约 33.4%；
- Bonus、Last、Correction Early、同步及其他阶段：约 38.5%。

这说明 HTP Tail 已经明显降低验证成本，但 Draft 与分层状态维护仍占大量时间。

### 4.5 HumanEval 结论

1. 异构自投机在前五题聚合上相对纯 CPU Target 获得了明确加速。
2. w4 的总体性能优于 w6，但最优窗口与题目相关。例如 002 的 w6 更快，而 000、003 的 w6 反而慢于 Target。
3. 高接受率主要由 001、002、004 三个生成 512 Token 的长样本贡献。高接受率只表示 Early 与 Target 一致，不等价于生成代码正确。
4. w6 Runner 记录前五题异构输出均与 CPU Target 一致，说明接受、回滚与 Bonus 逻辑在这些样本上保持了输出语义。
5. w4 测试期间电池温度约从 35.0 C 上升到 41.8 C。只有单次结果，尚不能完全排除热状态影响。

### 5.4 汇总结果

| 配置 | 总 Token | 总生成时间 | 聚合吞吐 | 微平均窗口接受率 | 相对 Target |
| --- | ---: | ---: | ---: | ---: | ---: |


### 5.5 阶段时间

| 配置 | Draft Build 合计 | Tail Verify 合计 | 总生成时间 |
| --- | ---: | ---: | ---: |
| w4 | 39.883 s | 44.986 s | 126.530 s |
| w6 | 54.522 s | 67.527 s | 153.708 s |

从 w4 增大到 w6 后：

- Draft Build 增加约 36.7%；
- Tail Verify 增加约 50.1%；
- 接受率反而从 63.115% 降到 55.369%。

因此，更长窗口并不自动带来更好的 HTP 利用率。若 Draft 质量不稳定，大窗口会增加验证 Batch 与回滚成本。

## 6. 输出一致性检查

CNN/DailyMail LM 五篇中：

- 00、01、02、04：CPU Target 与异构 w6 输出一致；
- 03：CPU Target 与异构 w6 输出不同；
- 03 的 HTP w4 与 HTP w6 输出彼此完全一致。

文章 03 的差异从输出约第 603 字节开始：

```text
CPU Target: Leeds midfielder Rudi Austin...
HTP Self:   "We've got to be better than that,"...
```

这一现象更像 CPU 完整 Target 与 CPU+HTP 分层 Target 的数值/后端差异，而不是窗口长度或投机接受逻辑错误，因为 w4 和 w6 在 HTP 上得到相同结果。

### 7.5 与论文对照

论文 Table 1 中，持续预训练的 LayerSkip Llama2-7B 在 CNN/DailyMail 1-shot 摘要上的报告值为：

| 模式 | E/window | ROUGE-2 | 接受率 | 吞吐 | 加速 |
| --- | --- | ---: | ---: | ---: | ---: |
| AR | - | 0.079 | - | 62.7 t/s | 1.00x |
| Self-spec | 8/12 | 0.078 | 68.9% | 127.9 t/s | 1.86x |

与随机 100 篇复现相比：

- ROUGE-2：`0.05752`，比论文低 `0.02048`，相对低约 26.3%；
- 接受率：`65.83%`，只比论文低约 3.07 个百分点；
- 吞吐：`51.69 t/s`，但 A40 与论文 H100 硬件不同，不能直接归因于实现；
- 输出同样经常复制原新闻，而不是生成高度压缩的摘要。

公开模型卡说明 `facebook/layerskip-llama2-7B` 是论文中的持续预训练 LayerSkip Llama2-7B，属于基础语言模型，并不是指令微调或摘要专用模型。论文还说明部分结果使用 Meta 内部代码库评测，公开 checkpoint、公开评测代码与论文内部环境不保证逐项完全一致。

因此，复制新闻正文的行为在官方 FP16 checkpoint、官方代码和服务器 GPU 上也存在，不能归因于：

- GGUF 转换；
- F16 量化误差；
- 手机 CPU/HTP 后端；
- 自投机验证逻辑。

ROUGE 仍可能非零，因为复制的新闻正文与 Reference Highlights 存在大量词面重叠。ROUGE 非零不代表模型确实生成了合格摘要。


## 8. 今日主要结论

1. CPU 前 8 层 Draft、HTP 后 24 层常驻验证已经能够稳定运行，且在 HumanEval 前五题取得 `1.60x` 的最佳聚合加速。
2. HumanEval 上 w4 优于 w6：`5.425 t/s` 对 `5.117 t/s`，窗口接受率也更高。
3. CNN/DailyMail 新闻续写上 w4 同样优于 w6：`5.058 t/s` 对 `4.164 t/s`，相对纯 CPU Target 分别为 `1.43x` 和 `1.18x`。
4. Window 越大不一定越快。低接受率样本会同时增加 Draft Build、Tail Verify 和回滚成本，甚至慢于 Target。
5. 当前性能瓶颈不只在 HTP Tail。CPU Draft、Bonus/Last/Correction Early、分层 KV 状态维护及同步仍占较大比例。
6. 大多数异构输出与 CPU Target 一致，表明主要 HTP F16 错误已经修复；CNN/DailyMail 第 03 篇仍需用 HTP `split-target-only` 做严格定位。
7. 官方服务器模型也会在摘要任务中复制原文。该现象属于公开 checkpoint/任务行为，不是手机或 GGUF 独有问题。
8. 当前实现的 Tail 是启动时常驻 HTP，不是每轮从闪存加载。闪存按需加载方案应作为独立实验，预计会引入显著 I/O 成本。
