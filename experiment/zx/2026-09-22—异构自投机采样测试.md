# 2026-09-22 异构自投机采样测试

## 1. 实验目的

本日实验在受控的 7 GiB 模型驻留预算下，验证 LayerSkip 自投机采样的正确性与性能，重点回答以下问题：

1. CPU 前 8 层 Draft、HTP 后 24 层 Target 验证在 Tail 权重流式加载时能否保持 Target 输出；
2. 将最后一个 Draft hidden state 合并进同一批 Tail 验证后，能否消除单独的 Last Tail；
3. `window=6/8/10` 对接受率、验证轮数、HTP 权重加载次数和吞吐的影响；
4. 在 HumanEval 前五题上，相对同为 7 GiB 预算的 CPU Target 能获得多少加速；
5. 当前剩余瓶颈位于 CPU Draft、UFS 读取、HTP 权重装载还是 Tail 验证。

本文中的自投机吞吐采用程序输出的 `layerskip generation`，不包含 Prompt Prefill。CPU Target 吞吐由 `eval time / runs` 计算，也不包含 Prompt Prefill。除特别说明外均为 Greedy decoding。

## 2. 实验环境


- 手机：OnePlus PJZ110
- SoC：Qualcomm SM8750
- 模型：`facebook/layerskip-llama2-7B`
- 模型格式：F16 GGUF
- 模型层数：32
- Early Exit：`E=8`
- CPU线程：4
- Draft：CPU执行 `[0, 8)` 层
- Target Tail：HTP执行 `[8, 32)` 层
- 最终LM Head：CPU
- 采样：Greedy
- 上下文：2048
- Batch：512
- UBatch：128
- 测试间冷却：60秒

## 3. 7 GiB模型驻留预算

本实验限制的是应用管理的模型驻留预算，不是Android系统级 `cgroup memory.max`。目标为：

```text
模型权重驻留 + 流式缓冲 + 运行时预留 <= 7 GiB
```

### 3.1 CPU Target规划

CPU Target命令使用：

```text
--model-resident-budget-mib 5632
--runtime-reserve-mib 1536
```

实测规划：

| 项目 | 字节 | 约MiB |
| --- | ---: | ---: |
| Fixed weights | 524,304,384 | 500.0 |
| Cached layers | 4,452,614,144 | 4,246.3 |
| Stream buffers，2层 | 809,566,208 | 772.1 |
| Runtime reserve | 1,610,612,736 | 1,536.0 |
| Planned total | 7,397,097,472 | 7,054.4 |

CPU Target常驻11个模型层，并使用当前层和下一层两个流式缓冲。前五题的Peak RSS约为6.64至6.65 GB，未超过7 GiB规划上限。

### 3.2 异构自投机规划

异构命令使用：

```text
--memory-budget-mib 7168
--runtime-reserve-mib 1536
--tail-stream-cluster-layers 4
```

实测规划：

| 项目 | 字节 | 说明 |
| --- | ---: | --- |
| Fixed weights | 524,304,384 | Embedding、LM Head等固定权重 |
| Early weights | 3,238,264,832 | CPU常驻前8层 |
| Cached Tail | 404,783,104 | 1个Tail层 |
| Stream buffer | 1,619,132,416 | 1个Slot，每次4层 |
| Runtime reserve | 1,610,612,736 | KV、计算图和运行时缓冲 |
| Planned total | 7,397,097,472 | 约6.89 GiB |

当前执行布局为：

```text
CPU DRAM:
  Early前8层
  KV cache
  固定权重与运行时缓冲

HTP/UFS Tail路径:
  1个Tail层缓存
  1个四层cluster流式Slot
  其余Tail层从UFS读取并装入HTP执行
```

## 4. Batched Bonus优化

### 4.1 修改前

旧实现完成一轮线性Draft后，会单独执行最后一个Draft位置：

```text
Draft D1...Dn
Target批量验证D1...Dn
Last Early
Last Tail
得到bonus logits
```

这会在每轮末尾额外执行一次Tail，并再次触发流式权重加载。

### 4.2 修改后

当前实现将最后一个Draft位置的Early hidden state直接加入同一批Tail验证：

```text
Draft D1...Dn，并保留Dn的Early hidden
Target一次批量处理全部hidden
同一批得到验证logits和bonus logits
```

实测所有新测试均为：

```text
phase last early = 0
phase last tail  = 0
```

### 4.3 CNN/DailyMail单样本前后对照

在修正末尾换行后的同一新闻续写Prompt、`window=10`、128 Token上：

| 指标 | 修改前 | Batched Bonus | 变化 |
| --- | ---: | ---: | ---: |
| 生成时间 | 641.452 s | 568.476 s | -11.4% |
| 吞吐 | 0.200 t/s | 0.225 t/s | +12.5% |
| HTP preload calls | 228 | 204 | -10.5% |
| HTP preload bytes | 353.78 GB | 316.54 GB | -10.5% |
| HTP preload time | 170.903 s | 147.073 s | -13.9% |
| Last Tail | 66.957 s | 0 s | 消除 |

修改前后接受计数和最终输出保持一致，说明优化只消除了冗余Tail执行，没有改变验证语义。

## 7. HumanEval聚合结果

五题共输出548 Token。CPU Target总生成时间使用各题 `eval time` 求和；异构总时间使用各题 `layerskip generation` 求和。CPU的 `eval time` 共对应543次逐Token decode；每题第一个输出Token来自Prompt末端logits，不计入 `eval time`，因此CPU聚合吞吐以543为分子。

| --- | ---: | ---: | ---: | ---: | ---: |

## 8. 输出一致性

### 8.1 比较方法

两个程序对特殊Token和输出结尾的显示方式不同：

- `llama-completion` 在普通输出末尾增加两个换行；
- CPU Target遇到EOS时显示 ` [end of text]`；
- `llama-layerskip` 遇到相同EOS时显示 `</s>`。

因此不能直接对原始文本文件执行 `cmp`。比较前需要：

1. 删除 `llama-completion` 额外添加的两个末尾换行；
2. 将 ` [end of text]` 和 `</s>` 视为相同EOS；
3. 再比较模型生成正文。

| 题目 | w6 | w8 | w10 | 说明 |
| --- | --- | --- | --- | --- |
| 000 | 一致 | 一致 | 一致 | 仅EOS显示字符串不同 |
| 001 | 一致 | 一致 | 一致 | CPU文件额外包含两个换行 |
| 002 | 一致 | 一致 | 一致 | 规范化前后哈希一致 |
| 003 | 一致 | 一致 | 一致 | 仅EOS显示字符串不同 |
| 004 | 一致 | 一致 | 一致 | 规范化前后哈希一致 |

五题的 `w6/w8/w10` 均保持CPU Target生成结果，说明以下逻辑在本组样本上正确：

- Draft接受；
- Target校验；
- Bonus token；
- KV rollback；
- Correction Early；
- Batched Bonus；
- 四层Tail cluster流式执行。

## 9. 生成内容与HumanEval质量

输出一致只说明自投机没有改变Target结果，不说明模型答案能够通过HumanEval测试。

| 题目 | Target生成行为 | 初步判断 |
| --- | --- | --- |
| 000 | 只检查相邻元素，且没有使用绝对差 | 不能覆盖完整题意 |
| 001 | 重复生成无意义的 `replace` | 错误且出现循环退化 |
| 002 | 首行正确实现小数部分，随后继续生成新函数并截断 | 使用HumanEval停止规则后可能正确 |
| 003 | 检查单个操作是否为负，没有检查累计余额 | 逻辑错误 |
| 004 | 前两行正确实现MAD，随后继续生成新函数并截断 | 使用HumanEval停止规则后可能正确 |

当前裸生成程序没有应用HumanEval常用停止条件，例如遇到新的顶层 `def`、`class` 或测试代码时截断。因此002和004虽然首先生成了正确实现，之后的无关续写可能导致整个文本出现语法错误。本文只将这组数据用于系统正确性和性能分析，不报告HumanEval pass@1。

## 10. CNN/DailyMail末尾换行诊断

此前2026-09-17记录中的CNN/DailyMail新闻续写Prompt保留了文件末尾的换行。该换行使模型进入重新生成新闻开头或复制正文的轨迹，造成异常高的Early/Target一致率。

修正为与标准 `llama-completion -f` 一致的Prompt后，同一文章的窗口接受率变为：

| 窗口 | 窗口接受率 |
| --- | ---: |
| w6 | 38.034% |
| w8 | 32.292% |
| w10 | 27.941% |
| w12 | 24.242% |

修正后CPU Target与异构输出逐字节一致。生成文本后半段仍出现段落循环，但该循环同样存在于CPU Target，因此属于模型自身的生成退化，不是异构验证引入的问题。旧记录中75%至86%的高接受率只代表保留末尾换行的旧工作负载，不能作为标准新闻续写结果。

## 11. 主要结论

1. 在应用规划的7 GiB模型驻留预算下，CPU Early 8层加HTP流式Tail可以正确完成LayerSkip自投机采样。
2. HumanEval前五题中，所有 `w6/w8/w10` 在规范化输出包装后均与CPU Target一致，没有发现接受、回滚或Bonus导致的Token错误。
3. Batched Bonus成功将 `phase last early` 和 `phase last tail` 降为0。在CNN/DailyMail单样本 `w10` 上，吞吐从0.200提升到0.225 t/s。
4. 五题聚合最优配置为 `window=8`，吞吐0.246 t/s，相对同预算CPU Target加速1.48x。
5. `window=10` 聚合吞吐0.245 t/s，与 `w8` 非常接近。更大的窗口降低接受率，但减少了验证轮数和HTP加载次数。
6. HumanEval/003的 `w6` 比CPU Target慢，说明接受率不足且验证轮数较多时，异构自投机不保证加速。
7. 当前瓶颈已经不是CPU Draft。`w8` 中Tail Verify占总生成时间96.82%，Draft仅占2.83%。
8. 7 GiB下绝对吞吐仍很低，主要原因是每轮验证都需要从UFS读取Tail cluster并向HTP重复装载权重。五题 `w8` 累计执行723次HTP preload，传输约1.12 TB权重。
9. 当前结果证明了有限驻留预算下的正确性和相对加速，但尚未达到常驻模型异构实验中的绝对吞吐。
