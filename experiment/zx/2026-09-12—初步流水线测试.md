# CPU-HTP 异构投机解码的初步流水线测试

## 1. 实验目的

- 测试累计路径概率、局部概率比和不同浅层树形是否能够提高有效旁支比例。
- 拆分 CPU Draft、Target host 调用、FastRPC/HTP 提交和 DSP 执行时间，建立 CPU/HTP 双泳道时间线。
- 在不改变生成结果的前提下，将当前树最后一层 Draft decode 与同一轮 Target 树验证重叠。
- 在 CNN/Daily Mail 上使用同一统一二进制进行串行/流水线严格 A/B，评估流水线的实际 Decode 收益。

本文记录的实验时间覆盖 2026-09-12 至 2026-09-13。所有性能实验均为 Decode 阶段测试，不把模型加载和 Prompt prefill 计入 Decode 吞吐。

## 2. 公共实验配置

- 设备：OnePlus PJZ110，Qualcomm SM8750，Android 16。
- Target：`qwen2.5-3b.q4_0.gguf`，放置在 HTP0，`-dev HTP0 -ngl 99`。
- Draft：`qwen2.5-0.5b.q4_0.gguf`，放置在 CPU，`-devd none -ngld 0`。
- CPU 线程：Target host、Draft 和 Draft batch 均为 4 线程。
- KV/context：`-c 2048`；CNN/DM 使用 `-c 4096`。
- Batch：单 Prompt 探索使用 `-b 128 -ub 128`；CNN/DM 使用 `-b 2048 -ub 128`。
- Flash Attention：`-fa off`。
- 单 Prompt：`Explain heterogeneous speculative decoding.`。
- 随机采样：`--temp 0.7 --top-k 4 --seed 1234 --ignore-eos`，除非表格特别注明。
- Greedy：`--temp 0 --top-k 1 --seed 1234 --ignore-eos`。
- 固定生成长度：`-n 128`；时间线诊断为降低 profile 开销使用 `-n 32`。
- 每个探索配置只运行一次，运行前冷却 30 或 60 秒。探索结果不能代替重复实验。

## 3. 流水线前的树结构补充实验

### 3.1 累计路径概率筛选

首先在 `<1,2,1,1>` 上将旁支筛选从单个 token 概率改为累计路径概率。窗口深度为 4。

| 路径阈值 | Decode 吞吐 | Drafted | Accepted | Verify | 窗口接受率 | Accepted/verify | Leaves/verify | Target verify/call | Tree build | Draft decode |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0.02 | 16.752 t/s | 262 | 81 | 48 | 42.19% | 1.688 | 1.729 | 101.221 ms | 2196.435 ms | 1952.292 ms |
| 0.05 | 18.826 t/s | 220 | 85 | 46 | 46.20% | 1.848 | 1.391 | 95.944 ms | 1908.395 ms | 1708.373 ms |
| 0.08 | **19.295 t/s** | 200 | 84 | 44 | **47.73%** | 1.909 | 1.273 | 97.749 ms | 1724.552 ms | 1556.344 ms |
| 0.10 | 17.111 t/s | 226 | 79 | 51 | 38.73% | 1.549 | 1.216 | 96.853 ms | 1928.079 ms | 1743.114 ms |

阈值从 0.02 提高到 0.08 后，无效旁支减少，Drafted、Tree build 和 Draft decode 同时下降；继续提高到 0.10 后，生成路径和 Verify 次数发生不利变化。累计路径概率能限制树规模，但单 Prompt 下仍没有超过同配置线性树。

## 4. 初步流水线实现

### 4.1 可重叠阶段

构造一棵深度为 4 的树时，最后一层 Draft decode 用于把最后一层 token 写入 Draft KV，并产生下一 token 的 logits。当前树的候选在调用前已经确定，因此这些 logits 不参与当前轮建树；但 KV 更新仍是下一轮 Draft 的依赖。

流水线实现采用以下边界：

1. 主线程完成当前树最后一层候选选择。
2. 工作线程异步执行最后一层 Draft decode。
3. 主线程同时准备并执行当前轮 Target 整树验证。
4. Target 验证完成后执行 `join_draft`。
5. 只有 Draft KV 更新完成后才允许进入下一轮。

因此这是“同一请求、同一轮内的最后一层重叠”，不是跨轮预测树，也不是多请求 serving pipeline。


### 4.2 双泳道与后端时间戳

`LLAMA_SPEC_TRACE=/path/trace.json` 生成 Chrome JSON trace，记录：

- CPU Draft/control：accept/sample、KV select、Draft seed、候选采样、普通 Draft decode、异步最后一层 Draft、DFS layout 和 join。
- HTP Target host interval：Target KV prepare 和整个 Target decode/synchronize 调用区间。

Hexagon 后端 profile 另外记录每个 OPBATCH 的：

- `host-submit-us`
- `host-receive-us`
- `host-span-us`
- DSP 报告的 OPBATCH usec 和 cycle

后续使用 `CLOCK_MONOTONIC/CLOCK_BOOTTIME` 锚点与真实 PID/TID 对齐 Perfetto CPU scheduler 数据。DSP cycle 时钟没有直接的 AP 同步 RPC，因此 DSP 执行块只能确定落在 submit/receive 区间内，不能声称获得了精确 DSP 起始时刻。

## 6. CPU/HTP 真实时间线诊断

### 6.1 Perfetto 与 Hexagon profile

使用 `cnn_dm_00`、`<1,2,1,1>`、Greedy、`p-split=0.40`、`n=32` 的时钟对齐结果：

| 指标 | 串行 | 流水线 |
| --- | ---: | ---: |
| Decoded token | 36 | 36 |
| Decode 时间 | 1.531 s | 1.369 s |
| Decode 吞吐 | 23.517 t/s | 26.298 t/s |
| Accepted / Verify | 26 / 9 | 26 / 9 |
| 窗口接受率 | 72.22% | 72.22% |
| Decode 期间进程 CPU core-time | 4569.667 ms | 4276.413 ms |
| 主线程 scheduled CPU time | 930.840 ms | 794.258 ms |
| Target host-call wall time | 935.974 ms | 847.020 ms |
| HTP submit-to-receive | 571.458 ms | 571.944 ms |
| DSP OPBATCH 执行 | 549.371 ms | 563.520 ms |
| submit/receive 减 DSP | 22.087 ms | 8.424 ms |

流水线吞吐单次提升 11.83%，Decode wall time 降低 10.58%。异步最后一层 Draft decode 为 141.874 ms，`join_draft` 总等待仅 0.022 ms，说明它几乎完全落入 Target 验证区间。

Target HTP 的 submit/receive 总时间在串行和流水线下几乎相同，DSP 工作量也没有下降，因此收益来自 CPU Draft 与 Target 调用的时间重叠，而不是 DSP 或 FastRPC 变快。

### 6.2 HTP 内部算子占比

另一组相同配置的 DSP profile 得到：

| 指标 | 串行 | 流水线 |
| --- | ---: | ---: |
| Target host verification | 922.359 ms | 854.299 ms |
| DSP OPBATCH 总时间 | 550.688 ms | 564.673 ms |
| `MUL_MAT + MUL_MAT+ADD` | 495.259 ms | 508.451 ms |
| Host interval 减 DSP | 371.671 ms | 289.626 ms |

矩阵乘约占 DSP batch 时间的 90%。该比例包含 Attention、FFN 等多个矩阵操作，不能直接全部标为 FFN。流水线没有减少 HTP 计算量，下一步应分别排查 Target host 区间和并行资源竞争，而不是优先优化 FastRPC 传输。

- 样本：`cnn_dm_00` 至 `cnn_dm_09`。
- 树形：`<1,2,1,1>`，`np=2`。
- 路径阈值：`p-split=0.30`；局部概率比关闭。
- 随机采样：`temp=0.7, top-k=4, seed=1234`。

## 9. 实验结论

- 扩大树、累计路径概率和局部概率比可以控制候选数量，但没有解决单 Prompt 上旁支利用率低的问题。真正多叶的最佳浅树仍低于线性树。
- 逐 token 诊断证明 Target 能正确进入并验证旁支，暂未发现树验证、KV、position 或祖先关系 mask 的明显正确性错误。当前瓶颈更接近候选质量和额外 Draft/Target 工作量。
- 最后一层 Draft decode 与当前轮 Target 验证存在安全且可观的重叠窗口。下一轮开始前的 join 保证 Draft KV 依赖不被破坏。
- 对齐时间线表明流水线没有减少 DSP 工作，也没有缩短 HTP submit/receive 区间；收益来自隐藏 CPU Draft wall time。
- CNN/DM 严格 A/B 中 10/10 样本获得正收益，平均吞吐提升 8.57%，窗口接受率和所有生成计数完全一致。初步流水线优化成立。
- 当前最后一层 Draft 已经几乎完全被覆盖，继续单纯扩大同一段重叠的空间有限。下一步应优先降低并行资源竞争，例如扫描异步 Draft 的 2/3/4 线程、固定 CPU affinity，并继续拆分 Target host 区间中的图构建、CPU fallback、HTP enqueue 和返回处理。
